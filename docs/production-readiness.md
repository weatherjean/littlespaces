## Implemented during this review

1. **Workspace ownership before writes.** Previously `main` opened/extended the database before `serve` acquired its lock, and administrative CLI commands never acquired it. `workspace::WorkspaceLock` now covers every CLI command and server startup before schema/key setup. Unsupported hosts fail closed. Regression tests verify exclusive ownership, release on close and no extension-table creation by a rejected CLI invocation.
2. **Atomic additive schema setup.** Extension tables/indexes previously committed in separate connections. They now install in one immediate transaction. A deliberately incompatible late table makes startup fail; the test verifies earlier tables were rolled back, base version remained unchanged, and a corrected retry/reopen succeeds.
3. **Durable cancellation.** The API previously acknowledged only an in-memory flag; restart could resume that job. Cancellation is persisted before acknowledgment and survives a dropped HTTP request. Recovery leaves it cancelled. Explicit continuation clears the flag, still refusing unknown call outcomes. A regression simulates death before the worker saves its terminal state.
4. **Terminal status persistence.** A failed final job update was discarded, allowing a finished worker to leave a permanently running job. The worker now retries only the idempotent status write and retains its active ownership. A database write lock exceeding the 250 ms busy timeout reproduces the old failure and verifies recovery. Persistent disk/storage failure still requires operator intervention; the host logs a bounded diagnostic.
5. **Accepted owner decisions survive disconnect.** Proposal execution now completes in a detached task, preserving the single-use claim. A test aborts the caller during database admission, verifies completion, and rejects a repeated decision. Process death during an unknown operation still requires review.
6. **Restart backoff.** Each provider attempt now durably reserves its minimum next backoff before transport, closing the crash window that allowed immediate retry. Normal transient failure policy remains one initial request plus three additional attempts with 10/20/30-second delays; longer provider Retry-After is honored within the existing 600-second bound. Completed tools are never retried by this mechanism.
7. **Production/development boundary.** Standard `--release` builds omit the live-test service and reject `development-fixtures`. The production smoke deliberately sets development environment flags and checks missing routes/key, embedded assets, actual SIGKILL/lock release, offline copy/restore, retained synthetic owner session and secret metadata, and cancellation recovery. CI now runs the optimized smoke on both configured architectures.
8. **App-scoped agent guidance.** Bound app chats now receive their app ID and explicit instructions to inspect `app_info {}` rather than rediscover the app through `list_apps`, then use read-only actions for factual questions. Existing nested schema/Rhai guidance was retained and real-model repair was rerun.
9. **Browser regression repairs.** Two old “Working…” selectors and a punctuation-dependent cancellation selector no longer matched the existing UI. They now check the actual live status region, Stop control and stopped state. The continuation test now waits for durable job completion rather than matching a pre-existing partial reply. No functional validation was removed.
10. **Documentation corrections.** Contributor guidance explains locks, release feature exclusion and smoke checks. Status no longer claims images/vision are absent or that implemented image bytes live outside SQLite.

## Remaining blockers, ranked

**P1 — hard resource containment is unproven.** Rhai executes inside the owner process. `runtime.rs` sets operation/call-depth/per-container limits, but these do not bound aggregate nested allocations, compilation or native JSON/SQLite work. `app_sqlite.rs` limits database/result size and uses a progress callback, but that is not a process memory boundary. Existing native-callback tests prove cancellation prevents late commits, not prompt preemption or survival under memory exhaustion. Required exit evidence: adversarial peak RSS/CPU measurements on the target host, concurrency tests and an explicit supported containment design. Do not remove the existing release warning.

**P1 — no released workspace upgrade/rollback contract.** `Store::create` accepts only application ID 1280528978 and user_version 4. Other versions fail without mutation; there is no host-schema migration chain. Version-4 extension setup is now atomic, but `CREATE TABLE IF NOT EXISTS` does not validate every historical table shape. Reproduction: the new failed-additive-installation test constructs an incompatible extension with version 4 and demonstrates safe failure, not conversion. Both preserved workspaces are version 4, which is not evidence that every earlier development database is compatible. There is also a concrete same-version downgrade hazard: HEAD `ebfefaa` uses workspace version 4 but its `AppCode` has no `sqlite` field and rejects unknown fields; a newly saved `sqlite:true` revision cannot be read by that older code despite sharing the workspace version. Before production, freeze/version the complete schema and define supported upgrades and binary downgrade behavior with fixtures. Never edit user_version to force acceptance or reset an existing workspace.

**P1 — target deployment and recovery qualification remain absent.** Optimized local tests passed, but current Linux AMD64/ARM64 jobs, reverse-proxy TLS/Host/OAuth behavior, deployment packaging and target-host backup restore have not been observed. The new offline drill uses synthetic local data and verifies session/secret metadata; it does not verify real OAuth refresh after disaster recovery, encrypted off-host backups, retention, disk-full behavior or power-loss durability. Rust advisory and final third-party notice review remain open.

**P2 — bounded history/retention is not implemented.** Calls, checkpoints, diagnostics, releases, image bytes and request events accumulate in the workspace. Reads are bounded, but durable storage is not. A release stores before/after SQL images (up to 8 MiB each) and records; repeated releases/uploads can fill the disk. Define owner-visible retention and backup capacity without deleting private evidence or recovery points implicitly.

**P2 — non-model interruption recovery is conservative.** Schedules advance `next_run` and claim a running job before invocation. Death between those steps leaves that occurrence interrupted after recovery rather than replaying it. Proposal outcomes can likewise require inspection if the process dies after a side effect but before its result is recorded. This avoids duplicate effects, but no comprehensive owner UI resolves every interrupted non-model operation. Add kill-point coverage and an explicit missed-occurrence/review policy before promising lossless scheduling.

**P2 — deployed frontend verification needs an operational choice.** An ordinary binary can serve and run published apps without Node, but a new frontend release needs the browser verifier or explicit owner preview approval. Automatic app-building promises require a supported verifier deployment and health/recovery behavior; the local dev harness is not that production service.

**P2 — physical device and external-service coverage.** Real microphone recognition/audio, native push delivery, mobile OS behavior and real account native web-search access remain unverified. App integration secrets are intentionally workspace-wide: every published backend can use any integration secret with public HTTPS. That is the documented trust model, not per-app credential isolation. SQL isolation, iframe sandbox/CSP, CSRF and SSRF tests do not establish a general adversarial security audit.

## Rollout and rollback once blockers are resolved

1. Finish review of the entire existing uncommitted change set, run observed Linux CI and package a locked ordinary release build with its frontend assets. Retain the prior binary and identify exactly which binary/schema a backup belongs to. Do not use a development-fixtures executable as the production artifact.
2. Inspect active jobs and uncertain external effects before stopping the host. Let work finish or explicitly cancel it. Stop the dev launcher as well as its Rust child/harness. Do not delete lock files or database sidecars to force startup.
3. With **all workspace processes stopped**, make a private copy of the complete workspace directory, including `workspace.sqlite`, `secrets.key` and any sidecars/files. Keep directory/file permissions restricted and store the backup outside the repository. The key and database are a pair; losing or replacing the key loses encrypted credentials. Local app release snapshots are not independent backups.
4. Restore that copy into a **new** private directory; never overwrite the only original. Run SQLite integrity/foreign-key checks and a restore drill with the matching binary. Keep the original stopped while testing a credential-bearing copy: concurrent restored instances can conflict over OAuth refresh and external work. Verify owner sign-in, secrets availability, app data/revisions and recovery state before switching traffic.
5. For binary rollback, stop the new host and restore the **matching pre-upgrade directory and prior binary**. Do not assume a prior binary understands new schema/data. Preserve the failed-upgrade directory for diagnosis. OAuth refresh rotation may require reconnecting after restoring older credentials; never import tokens from private caches.
6. For app-only rollback, prepare a tested code revert retaining current data, or review an explicit snapshot/selective-preservation plan. Reject stale plans. These operations do not undo remote HTTP effects, delivered notifications, uploads or schedule execution; inspect durable effect evidence before any repeat.

These steps document a future controlled rollout. They do not authorize deployment or certify the unresolved blockers.
